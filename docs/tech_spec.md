## 4. Фаза 1: Умный Список Покупок (Shopping List Logic)
**Задача:** Реализовать разделение интерфейса на две вкладки: "Склад" и "Список покупок".

### Логика работы
1. **Вкладка "Склад" (Inventory):**
   - Отображает ВСЕ товары.
   - Позволяет менять `current_quantity` (+/-).
   - Позволяет задать `min_threshold` (настройку) для каждого товара.

2. **Вкладка "Список покупок" (Shopping List):**
   - Отображает ТОЛЬКО те товары, где `current_quantity < min_threshold`.
   - **Manual Override:** (Опционально) Позволяет вручную добавить товар в список, даже если его много (флаг `force_to_buy`).

3. **Сценарий "Покупка":**
   - Пользователь находится в магазине во вкладке "Список покупок".
   - Нажимает кнопку "Куплено" (Done) у товара.
   - Система:
     1. Увеличивает `current_quantity` (по умолчанию +1 или +`min_threshold`).
     2. Товар исчезает из списка покупок (так как условие `current < min` перестает выполняться).

## 5. Фаза 4: Логистика и Магазины (v0.4.0)
**Цель:** Оптимизация маршрута закупок.

### Структура БД (Таблица `shops`)
| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | int8 | ID магазина |
| `name` | text | Название (Рынок, Пятерочка) |

**Связь:** `inventory_items` имеет поле `shop_id` (Foreign Key).

### Логика работы (Стратегия v1)
1. **Принцип "Один товар — Одна запись":**
   - Мы НЕ создаем дубли товаров для разных магазинов ("Картошка Рынок", "Картошка Магазин").
   - Товар существует в единственном экземпляре.
2. **Поле `shop_id`:**
   - Означает "Предпочтительное место покупки" или "План на следующую закупку".
   - Пользователь меняет магазин в карточке товара, если в этот раз планирует купить его в другом месте.
3. **Интерфейс:**
   - Вкладка "Список покупок" группирует товары по названию магазина.

## 6. Фаза 5: "Magic Input" и AI-Интеграция (v0.5.0)
**Цель:** Реализация концепции Zero UI. Управление системой через естественный язык.

### Специальная логика: "Спортивный Шифр" (Bicep Protocol)
**Проблема:** Отслеживание прогресса по каждой руке + автоматический подсчет времени.
**Решение:** Пользователь вводит строку цифр (напр. "543322").
**Алгоритм обработки (внутри AI Prompt):**
1. **Декодирование сетов (`val_text`):**
   - Нечетные цифры последовательности -> Правая рука.
   - Четные цифры -> Левая рука.
   - Формат вывода: `П: 5-3-2 | Л: 4-3-2`.
2. **Расчет времени (`val_num`):**
   - Формула: $T_{total} = (Sum_{reps} \times 4s) + (N_{rests} \times 30s) + T_{warmup}$
   - Где $T_{warmup} = 120s$ (фиксированный прогрев).
   - Результат округляется до целых минут в большую сторону.

### Архитектура AI
- **Провайдер:** Google Gemini (Model: `gemini-1.5-flash`).
- **Метод:** Client-side integration (через `aiAssistant.js`).
- **Prompt Engineering:** Системные инструкции вынесены в `prompts.js` для безопасной настройки тона и правил разбора.

### Новые сущности БД
1. **`activities` (Справочник активностей):**
   - Типы: Спорт, Привычки, Рутина.
   - Поля: `name`, `category`.
2. **`activity_logs` (Журнал действий):**
   - Хранит выполнение (Бицепс — 4 подхода).
   - Поля: `value_numeric`, `value_text`.
3. **`journal` (Дневник):**
   - Хранит рефлексию и мысли.
   - Поля: `content`, `tags`.

### Логика "Magic Input"
1. Пользователь вводит текст (или диктует).
2. Текст + Текущее состояние склада + Список привычек отправляются в LLM.
3. LLM возвращает JSON-массив команд (`inventory`, `activity`, `journal`).
4. Фронтенд выполняет команды параллельно.
